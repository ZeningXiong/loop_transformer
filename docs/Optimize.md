# SenseNova-Loop-9B-Preview 本地运行优化记录

目标：在 RTX 4070 Laptop（8GB 显存）+ 不超过 8GB 内存（RAM）的条件下运行 loop 模型 SenseNova-Loop-9B-Preview。运行时不从 SSD 大量读取权重（这是放弃 235B 流式方案、改用 loop 模型的原因），并尽量接近原始 bf16 模型的输出。

- 硬件：Ryzen 9 7845HX，32GB 内存（测试时没有用 memhog 锁定），RTX 4070 Laptop 8GB，Windows 11
- 软件：项目内独立虚拟环境 `.venv`（复用全局 torch 2.5.1+cu124）、transformers 5.18.0、bitsandbytes 0.50.2、triton-windows 3.1.0、flash-linear-attention 0.3.2
- 模型：9.4B 参数。32 层解码器，其中第 4–27 层用同一份权重跑两遍，每个 token 共 56 次层计算。每 4 层里 3 层线性注意力（Gated DeltaNet）+ 1 层全注意力，循环部分用 mHC 双残差流。词表 248,320，原始权重是 FP32（38GB）。

> 本文只保留**有提升**的改动，每条给出效果和实测数字；试过但没有提升的方法集中列在最后一节，一句话带过。章节编号沿用历史记录，方便和以前的讨论对照。

## 2. lm_head 也量化，embedding 和视觉模块放到 CPU

- **改了什么**：lm_head（248320×4096）改为 NF4；embedding（约 2GB）和视觉模块用 device_map 放到 CPU。
- **结果**：模型常驻显存 **8.90 → 4.48GB**，峰值 6.62GB。速度没有变化——说明之前慢的主要原因不是显存溢出（第 5 步才找到真正原因）。
- **不严谨之处**：embedding 用的是 accelerate 的"CPU 卸载"，这个模式本身是瓶颈，第 5 步换掉了。lm_head 量化后个别措辞有变化，当时没有做量化评估。

## 4. 用 profiler 找瓶颈：把 mHC 的 Sinkhorn 融合成一个内核

- **发现**：20 个 token 里 `logsumexp` 被调用 153,600 次，加上子运算占 CPU 侧时间的 **96%**。原因是 mHC 路由器对 2×2 矩阵做 20 轮 Sinkhorn 迭代，每层 2 个路由器 × 56 次层计算 = 每个 token 几千次极小的 GPU 运算发起。
- **改了什么**：`patch_sinkhorn()` 在运行时把模块里的 `sinkhorn` 换成 `torch.compile` 版本，不改模型文件。
- **结果**：单次调用 **2054 → 273µs**（误差约 1e-7），profiler 下 1.11 → 1.91 tok/s。
- **不严谨之处**：首次调用要编译约 15 秒，没做编译缓存；只适用于用 mHC 的模型。

## 5. embedding 真正在 CPU 上计算

- **发现**：accelerate 的"CPU 卸载"会在每次前向把**整张 2GB 词表**复制到 GPU（`copy_` 每次约 120ms，每 token 2 次）。
- **改了什么**：`CpuEmbedding` —— 在 CPU 上只查出需要的那几行，再送到 GPU。
- **结果**：实际 **6–7.5 tok/s**（相比起点约 4 倍），输出逐字相同。

## 7. 离线 NF4 + SSD 读 embedding + 不加载视觉模块

- **改了什么**：
  - `convert_nf4.py`：逐张量读取 → GPU 量化 → 写成 512MB 分片，249 个量化层的结果与 transformers 在线量化**逐位一致**。
  - `load("offline")`：meta 设备上搭空结构，逐个张量从文件直接送进 GPU；文本模式不创建视觉模块、不加载 MTP 头。
  - embedding 存成原始 bf16 文件（每行 8KB），`SsdEmbedding` 按偏移只读需要的行，不在内存里保留整张词表。
- **结果**：加载 **47 → 7–8 秒**；加载峰值内存 **10.1 → 2.2GB**，生成时 6.9 → 2.6GB；11 道题输出逐字相同；新模型目录 6.53GB。
- **SSD 冷读实测**：每行 0.4–0.6ms，每 token 只读 1 行，占单 token 耗时（约 135ms）不到 1%。
- **不严谨之处**：8GB 内存的结论是在本机 32GB 下测进程峰值得出的，**没有用 memhog 锁定 8GB 实测**。

## 9. 按层混合精度（NF4 / int8）+ 自写 int8 内核

- **改了什么**：
  - `convert_int8.py`：所有线性层另存一份**只量化权重**的 int8（每输出通道一个缩放系数，7.94GB）。没用 bnb 的 LLM.int8，因为它把激活也量化了。
  - 模型分 65 组（32 层 × 注意力/MLP + lm_head），每次只把一组从 NF4 升级到 int8，在搜索集（8 段 × 256 token）测 KL 降幅，按"每 GB 显存降多少 KL"贪心，每个预算点再在另外 8 段验证集上复测。
- **结果（误差 vs 显存）**：

| 额外显存 | 升级组数 | 验证集 KL | 验证集首选一致 | 常驻显存 |
|---:|---:|---:|---:|---:|
| 0（全 NF4） | 0 | 0.146 | 85.9% | 4.50 GB |
| +0.5 GB | 16 | 0.093 | 88.1% | 5.00 GB |
| **+1.0 GB（现用）** | **25** | **0.078** | **88.3%** | **5.48 GB** |
| +1.5 GB | 34 | 0.064 | 89.6% | 6.00 GB |
| +2.0 GB | 43 | 0.050 | 90.4% | 6.48 GB |
| +2.5 GB | 51 | 0.040 | 90.9% | 6.97 GB |
| +3.0 GB | 53 | 0.033 | 93.0% | 7.45 GB |

- **规律**：注意力层性价比最高（前 11 名里 10 个是注意力层），前几层（L00–L04）最敏感；有 11 组单独升级后误差反而**略微变大**，说明各组误差会互相抵消、**不能简单相加**，所以每个预算点都是重新实测的组合。+2.0GB 方案在短 prompt 下整卡就到 8.54GB 超限（见第 11 步），已撤回，现用 +1.0GB。
- **int8 的速度问题与解法**：int8 层最初"先还原成 bf16 再矩阵乘"，速度从 7.1 掉到 4.3 tok/s；自己写了 Triton 内核 `int8_gemv.py`（直接读 int8 权重做单 token 矩阵乘，约 230GB/s），**快约 5 倍**，混合方案速度回到 **7.2–7.5 tok/s**，和全 NF4 一样。该内核与模型无关，可复用。
- **不严谨之处**：搜索集/验证集各约 2000–3000 个位置，文本类型有限；贪心排序不保证全局最优；decode 用 Triton 内核、prompt 用"还原+矩阵乘"，舍入方式不同，同一题的答案偶尔会变。

## 10. 长 prompt 显存暴涨：注意力退回到了最原始的实现

- **原因**：全注意力是 16 查询头对 4 组 K/V（GQA）。transformers 默认 CUDA 上有 FlashAttention，于是传 `enable_gqa=True`，但 **Windows 版 PyTorch 没有 FlashAttention**，而 torch 2.5 的省显存后端又不支持 `enable_gqa`，于是悄悄退回 MATH 实现，生成了完整的 16×T×T 分数矩阵（2048 token 时 1.08GB，按长度平方增长）。
- **改了什么**：`use_memory_efficient_attention()` —— 让 transformers 先把 K/V 复制成 16 份再算，就能用上省显存实现。
- **结果**：prompt 2048 时临时显存 **1.15 → 0.33GB**，处理时间 **5.55 → 2.41 秒**；4096 / 8192 也能跑了。验证集 KL 0.0501 → 0.0503，精度不受影响。

## 11. 分块处理 prompt + 自写生成循环 + 整卡显存保护

- **改了什么**：`generate_chunked()` 把 prompt 切成固定大小的块（512 token）逐块送入，传正确的位置编号（只处理文本时三维位置编码三行相同，直接传位置编号是精确的）；线性注意力状态和全注意力 KV 在块之间自动接续。逐 token 生成也自己写，为后面的 CUDA Graph 打底。transformers 自带的 `prefill_chunk_size` 在这个模型上会算错三维位置编码，不能用。另加 `VramGuard`：后台每 20ms 查整卡显存，到物理上限 97% 就中止。
- **正确性**：与 transformers `generate` 的 40 个 token 逐字相同；分块与一次性处理的第一个 token 分布 KL 为 6e-5–4e-4，比量化误差小两三个数量级。
- **结果（全 NF4、每块 512）**：

| prompt 长度 | 本进程显存增量 | 整卡峰值 | 处理 prompt | 生成速度 |
|---:|---:|---:|---:|---:|
| 2048 | 0.37 GB | 6.18 GB | 3.1 s | 7.9 tok/s |
| 4096 | 0.49 GB | 6.38 GB | 6.2 s | 7.9 tok/s |
| 8192 | 0.74 GB | 7.42 GB | 12.7 s | 7.2 tok/s |

  处理 prompt 的临时显存现在**只取决于块大小**（约 0.25GB），随长度增长的只剩 KV cache（每 token 57KB）。

## 12. 固定 KV 缓冲区 + 不复制 K/V 的注意力 + 启动预热

- **改了什么**：
  - `make_fixed_cache()`：仍是 `DynamicCache`，但把 14 个全注意力槽位换成 `FixedKVLayer` —— 启动时一次性分配 `[1, 4, max_len, 256]`，`update()` 原地写入并返回视图，不再拼接/重新分配。
  - `gqa_fold_attention()`：把共用一组 K/V 的 4 个查询头沿序列方向合并，不需要 `enable_gqa`、也不复制 K/V（第 10 步的复制在 32k 时每次调用要多约 0.5GB），并**强制只用省显存后端**，不会再悄悄退回原始实现。
  - `warm_up()`：先用小缓冲区把首块 / 续块 / 逐 token 三条路径各跑一遍，Triton 编译完再分配大缓冲区。
- **结果**：消掉了第 11 步发现的"每 token 重分配一次 KV"造成的约 1GB 碎片（8192 token 时整卡比实际需要多约 1GB）；1500 token 时首 token 分布 KL 3e-5，生成的 32 个 token 完全相同。

## 13. KV cache 存成 int8：32k 上下文放下了

- **改了什么**：`FixedKVLayer` 增加 int8 模式。K/V 按"每个 token、每个头"对称 int8 量化，各配一个 fp32 缩放系数；所有层共用一块预分配的 bf16 临时缓冲区，每层算注意力前把已写入部分还原进去。
- **精度**（4096 token 文本，逐位置与 bf16 KV 比）：

| 位置 | KL | 首选一致 |
|---|---:|---:|
| 0–1024 | 2.6e-3 | 98.4% |
| 1024–2048 | 8.5e-3 | 98.0% |
| 2048–4096 | 1.0e-2 | 98.5% |

  误差约是 NF4 权重量化误差（0.146）的 2–7%，随位置略微增长。
- **32k 结果**（全 NF4 + int8 KV + 每块 256）：

| | 8192 token | 32768 token |
|---|---:|---:|
| 整卡显存峰值 | 7.66 GB | **7.74 GB** |
| 处理 prompt | 14.9 s（548 token/s） | 57.6 s（569 token/s） |
| 生成速度 | 7.6 tok/s | 7.7 tok/s |

  32k 的 KV：int8 存 0.96GB + 还原缓冲 0.13GB（bf16 时是 1.88GB）；从 8k 到 32k 整卡只多 0.08GB，生成速度不降。每块 512 时 32k 会到 8.36GB 被保护中止，所以用 256（处理 prompt 慢约 30%）。
- **不严谨之处**：精度只测到 4096 token；32k 用同一批文本重复拼接，不代表真正的长文本理解；K 按 token 量化不是最优（KIVI 是 K 按通道、V 按 token，未试）；分配约 1.09GB 时整卡实际涨约 1.62GB，多出的约 0.5GB 不在 PyTorch 统计里，未解释。

## 14. 自投机解码（用模型自带的 MTP 头）

- **原理**：模型自带一个 MTP 头（`mtp.safetensors`，0.24B 参数 bf16，0.49GB），transformers 不加载它，这里用 Qwen3.5 的组件自己搭（`sn_spec.py` 的 `MTPHead`）。每步：MTP 根据（上一位置隐藏状态、当前 token）猜出下一个 token d → 主模型一次处理 `[x, d]` 验证 → 命中则一次前向得 2 个 token；未命中则回退（复制线性注意力状态、KV 写指针回调）并用正确的 token 重算。
- **接法**（实测确定）：用主模型**最终 norm 之后**的隐藏状态、**embedding 在前**拼接，命中率 57%；反过来只有 0.1%。
- **结果**（全 NF4，各生成 200 token）：

| 问题 | 普通 | 自投机 | 倍数 | 命中率 |
|---|---:|---:|---:|---:|
| 中文介绍 | 8.0 | 7.2 | ×0.91 | 0/4（退回普通生成） |
| 写代码 | 8.0 | 9.6 | ×1.19 | 88% |
| 英文解释 | 7.9 | 8.1 | ×1.03 | 68% |
| 推理（开思考） | 8.1 | 10.2 | ×1.25 | 95% |
| 合计 | 8.0 | **9.0** | **×1.12** | — |

- **各环节耗时**：主模型 1 token 约 120ms；验证 2 个 token 约 1.25–1.7 倍（见第 21 步，去掉补丁后更便宜）；lm_head 每行 2.4ms；MTP 头 2.8ms。**命中率要高于约 63% 才比普通生成快**，所以加了门限：命中率低于 60% 时退回普通生成 16 个 token 再试。
- **不严谨之处**：只测了 4 个问题；"输出一致"只在浮点误差范围内成立（4 题里 2 题中途措辞不同，都合理）；MTP 头 0.49GB，**和 32k 配置不能同时开**，要先把它量化成 NF4（约省 0.35GB）。

## 17. CUDA Graph 解码

- **改了什么**：
  - `cudagraph_decode.py` 把第 12 步的 `FixedKVLayer` 换成图友好的 `GraphKVLayer`，三处必须静态化的地方分别处理：①**写入位置**改成 `index_copy_`，索引放在设备缓冲区里、每步由图外填一次；②**读取长度**改成固定 `pad`（按桶 256/512/…/32768），不再返回随 token 增长的视图；③**掩码**由调用方显式给出 `[1,1,1,pad]` 布尔掩码（原 `gqa_fold_attention` 在单 token 时直接丢掉掩码，这里补了 `masked_fold_attention`）。token/position 都写进静态缓冲区再重放；embedding 是 SSD 上的 Python 读，留在图外。
  - 每个桶第一次用到时才捕获（0.3–0.4 秒）。
- **正确性**：200 token 上下文贪心生成 31 个 token，图解码与逐层 eager **逐 token 完全相同**，首步 logits **KL = 0、最大绝对差 = 0**（位级一致）。
- **测速**（+1.0GB 方案、Sinkhorn 已编译、每步同步计时取中位数）：

| 上下文 | 逐层 eager | CUDA Graph | 提升 |
|---|---:|---:|---:|
| 128 | 7.12 tok/s（140 ms） | **9.30 tok/s（108 ms）** | ×1.31 |
| 512 | 7.54 tok/s（133 ms） | **9.02 tok/s（111 ms）** | ×1.20 |
| 2048 | 7.38 tok/s（135 ms） | **8.82 tok/s（113 ms）** | ×1.19 |

  显存几乎不变（图私有内存池 < 0.1GB），精度零影响。图：`cudagraph_compare.png`。
- **为什么只有 ×1.2**：内核级 profile 显示一个 decode 步里 244 次 `gemm_4bit` 约占 30ms，其余 70 多毫秒是几千个 `mul / copy_ / _to_copy / cat / mean` 小算子；图重放省掉的是 **CPU 提交**（约 10ms），GPU 上要执行的算子一个都没少。**这一步是 GPU 执行受限，不是提交受限。**
- **一步的去向（实测，按子系统分组）**：

| 子系统 | ms/步 | 次数/步 |
|---|---:|---:|
| `bitsandbytes::gemm_4bit` | 29.8 | 244 |
| mHC / Sinkhorn 编译区 | 16.3 | 96 |
| FLA / 线性注意力 | 2.0 | 410 |
| 卷积（cuDNN 回退） | 0.6 | 84 |
| 注意力 / softmax | 0.5 | 28 |
| 其余（元素级长尾） | ~60 | 数千 |

## 21. 去掉 `small_batch_gemv` 补丁

- **背景**：第 14 步为了绕开"bnb 在 2–4 行时很慢"，把 2–4 行的前向拆成逐行调用（`small_batch_gemv`）。实测发现这个前提在 bnb 0.50.2 上已经不成立：**原生多行路径本来就读一次权重**（q_proj [8192,4096]：1 行 153.3µs、**2 行 153.7µs**、4 行 255.0µs），而逐行循环是 160 / 263 / 468µs。
- **改了什么**：删掉 `test_spec.py`、`probe_spec_cost.py`、`bench_spec16k.py`、`bench_spec4.py`、`run_cudagraph.py` 里的 `small_batch_gemv()` 调用（定义留在 `sn_spec.py` 供对照实验用）。
- **结果**（2K 上下文、+1.0GB 方案）：

| 配置 | 1 token | 2 token | 4 token |
|---|---:|---:|---:|
| 带补丁 | 127.0 ms | 272.4 ms（×2.15） | 344.6 ms（×2.71） |
| **去掉补丁** | 139.8 ms | **239.2 ms（×1.71）** | **284.6 ms（×2.04）** |

- **对投机解码的影响**：2-token 验证从 ×2.15 降到 ×1.71，100% 命中率下的预期加速从 `2/2.15 = 0.93×`（净亏）变成 `2/1.71 = 1.17×`（净赚）。1 token 那列的差异是测量漂移（补丁不碰单行路径）。

## 22. int8 层在 2–4 行时会把整张权重反量化——2-token 变慢的真正主因

- **怎么找到的**：把 106 个 int8 层逐个在 T=1 / T=2 下计时（`bench_int8_rows.py`）。

| | T=1 合计 | T=2 合计 |
|---|---:|---:|
| 现状 | 16.1 ms | **89.2 ms（+73.1 ms）** |
| 改成逐行调用快内核 | 16.1 ms | **29.9 ms（+13.7 ms）** |

  2-token 相对 1-token 只多约 99ms，**其中 73ms 来自这 106 个 int8 层**（占 74%）。单层看最夸张：`down_proj` 352 → 2197µs（×6.2），逐行调用只要 839µs。
- **原因**：`Int8WOLinear.forward` 只有"单 token → Triton int8 GEMV"这一条快路径；其余情况走 `_int8_linear`，也就是 **`q.to(x.dtype)` 把整张 int8 权重还原成 bf16 再矩阵乘**。全模型 106 层、2.23GB int8，等于每次 2–4 行的前向都要转换约 4.5GB。
- **修复**：2–4 行时逐行调用 `int8_gemv`（`sn_loop_common.Int8WOLinear`）。
- **端到端结果**（2K 上下文、+1.0GB 方案、无 `small_batch_gemv` 补丁）：

| | 1 token | 2 token | 4 token |
|---|---:|---:|---:|
| 修复前 | 139.8 ms | 239.2 ms（×1.71） | 284.6 ms（×2.04） |
| **修复后** | 124.6 ms | **150.1 ms（×1.20）** | **235.7 ms（×1.89）** |

- **对投机解码的意义**：2-token 验证从 ×1.71 降到 **×1.20**，100% 命中率下的预期加速从 1.17× 变成 **1.67×**（最早带补丁时是 0.93×，净亏）。
- **还剩的部分**：4-token 仍是 ×1.89，来自 bnb 的 NF4 路径在 4 行时从 153µs 涨到 255µs（2 行仍是 153.7µs）。也就是说 **2 行验证已经接近最优，4 行要另想办法**（k 行 NF4 内核实测 344µs，比 bnb 的 255µs 还差，见第 20 步）。

- **22b. 2-token 验证的 CUDA Graph**（`cudagraph_spec.py`）：把单 token 图的三套静态化办法推广到 q_len=2（2 个索引的 `index_copy_`、`[1,1,2,pad]` 掩码），捕获成功、输出正确。**但重放本身比 eager 慢 10%，而且捕获要 4.2 秒**（`probe_graph_replay.py`，16K、同一份缓存、同一状态）：

| | 耗时 |
|---|---:|
| 纯图重放（无任何 Python 准备） | 161.5 ms |
| 完整 `dec.step`（准备 + 重放） | 165.6 ms |
| eager 前向（同一状态） | **146.7 ms** |
| 捕获一次 | **4159 ms** |

  之前看到的"400–512 ms/步"是**把 4.2 秒的捕获摊进 12 步的测量**（4159/12 + 165 ≈ 511 ms），不是重放本身慢。真实情况是：16K 下一步本来就是 GPU 计算受限，图要去掉的 CPU 提交只占约 10 ms / 147 ms，而固定 `pad`（16440）+ 显式 16K 掩码又吃掉了一点，净结果是 −10%。**结论：2-token 验证不值得上图**；单 token 在短上下文仍然值得（×1.19–1.31）。

## 23. 2×2 Sinkhorn 的闭式解：一步 decode 省 23%

- **为什么盯上它**：消融发现 mHC 路由整体占 **28.4 ms/步**，其中 **sinkhorn 占 25.2 ms**（非 sinkhorn 的 norm+fp32 GEMV 只有 3.1 ms）。它每 token 被调用 **112 次**（2 个 router × 56 次层执行），成本主要不是那 20 轮数学，而是每次调用都要过一遍 Dynamo 守卫。
- **数学**：2×2 的双随机矩阵必然形如 `[[p, 1-p], [1-p, p]]`，而 `p` 由交叉比唯一确定——对角缩放不改变 `ad/bc`，所以整条迭代轨迹都由它决定。于是 20 轮「行归一化 + 列归一化」可以换成一次 sigmoid：

  `p = sigmoid((a + d − b − c) / 2)`（a,b,c,d 是 log 域四个元素）

  实测：这就是精确极限，而 20 轮迭代在真实量级上**还没收敛**（logits×1 时差 4.2e-3，×20 时差 2.5e-2；跑到 200 轮才收敛到 2.4e-7）。
- **速度**（200 token 上下文、1 token、同缓存同状态）：

| 配置 | 一步 decode |
|---|---:|
| 现状（20 轮 + torch.compile） | 125.0 ms |
| **闭式解** | **96.7 ms（省 28.3 ms，23%）** |
| 换回现状（确认无漂移） | 130.3 ms |

- **任务级验证**（8 道数学题 + 2 个开放问题，对话模板、不开思考）：

| | 结果 |
|---|---|
| 数学题（不开思考） | **8/8 完全一致**（连答错的 4 道也是同样的错：214、1024、1601、222） |
| 数学题（**开思考**） | **两种实现都 8/8 全对，最终答案 8/8 一致**；思考过程长度几乎一样（9 题共 446 vs 444 token，逐题只有一道差 2 个 token：33 vs 31） |
| 开放问题 | 2 个里 1 个逐字相同（Python 回文函数），杜甫那题从第二句起措辞不同 |

  也就是说：数值上换了（KL 0.665 相对现状），但**任务行为没有变化**——不开思考时答案逐字相同，开思考时连思考过程的长度都几乎一样（446 vs 444 token），说明模型的推理轨迹基本没被影响。
- **接入方式**：`sn_loop_common.load_offline()` 里默认启用（`fast_sinkhorn.enable(True)`）；`streams > 2` 的模型仍走原实现。要回退只需 `fast_sinkhorn.enable(False)`。
- **不严谨之处**：任务级只测了 8 道数学题 + 2 个开放问题，样本小；开放式措辞确实会变（合理范围），长文/代码任务没有系统评测。

- **24. 推理时把循环块跑 4 遍**：8K 上下文、104 次层执行、26 个全注意力槽位，耗时 **×1.89**（8.37 → 4.44 tok/s），输出退化成不成句的代码（`_matrix = torch.randn( cross stream mixing weight shape ...`），而 2 遍时续写的是合法 Python。**循环次数是训练时定死的，推理时加循环等于换了一个函数**，不能这么提速。顺带：prefill 只从 30.9s 涨到 35.2s（+14%），说明 prefill 主要花在 8K 注意力上而不是层计算。

## 25. MTP 头量化成 NF4：省 0.35 GB，速度与命中率不变

- **做法**：`MTPHead` 里的 8 个 `nn.Linear`（fc + 全注意力层的 q/k/v/o + mlp 三层）原地换成 bnb 的 NF4 `Linear4bit`（`test_mtp_nf4.py`）。`lm_head` 和 `embed_tokens` 本来就是共享的，不重复量化。
- **显存**：

| 配置 | MTP 头 | 本进程 | 整卡（静态） | 16K 运行峰值 |
|---|---:|---:|---:|---:|
| 全 NF4 权重 | bf16 | 5.60 GB | 7.28 GB | 8.02 GB |
| 全 NF4 权重 | **NF4** | **5.25 GB** | **6.53 GB** | **7.66 GB** |
| +1.0GB int8 权重 | **NF4** | 6.22 GB | 7.71 GB | **8.59 GB（仍超）** |

- **质量/速度**（16K、全 NF4、KV int8、闭式解 sinkhorn，同一次 prefill 后分段计时）：

| MTP 头 | 1-token 前向 | 2-token 前向 | 自投机 | 整卡 |
|---|---:|---:|---:|---:|
| bf16 | 159.0 ms | 168.4 ms | 10.25 tok/s（195 ms/步） | ~7.0 GB |
| **NF4** | 163.6 ms | 166.5 ms | **10.77 tok/s（186 ms/步）** | **~6.7 GB** |

  两种头都是 12/12 全中，速度差异在噪声内——草稿错了只是回退，最终 token 仍由主模型决定。
- **⚠️ 更正一个错误结论**：中途有几次同配置只测到 **4.2 tok/s**，我当时归因为“机器状态漂移”，**错了**。实测 GPU 频率全程钉在 **2460 MHz / 8001 MHz**（温度 60–62 °C，功耗 50–70 W），没有降频；真正的原因是那几次的**整卡峰值到了 8.02–8.59 GB**（贴着 8.59 GB 的卡上限），Windows 开始借内存，速度掉一半。快的那些跑在 **6.7–7.1 GB**。所以判断标准应该是“整卡峰值离 8.59 GB 还有多少”，而不是时间点。

- **25b. 一次验证 3 / 4 / 6 个 token**（16K、全 NF4、NF4 MTP、KV int8、闭式解 sinkhorn，剔除前 3 步预热后的稳态）：2 token **10.56 tok/s** ＞ 3 token 9.25 ＞ 4 token 8.71 ＞ 6 token 6.91。逐位命中率 100% / 22–37% / 12% / 0% / 0%——**多草稿不划算**：每步代价涨得比提交量快（189 → 324 → 367 → 521 ms/步，提交只有 2.00 → 2.67 → 3.00 → 3.00）。**结论：保持 2-token，真正该提升的是草稿质量而不是草稿数量。**
  - **顺带发现一个重要的测量陷阱**：prefill 之后的**前 3 步极慢**（实测首阶段 1356 ms/步，稳态 189 ms/步），原因是 16K KV 缓冲首次触碰的缺页 + 内核 autotune。不剔除这几步，会把先跑的配置算慢 2–7 倍——之前“3-token 比 2-token 快”的假象就是这么来的。

- **25c. 多草稿为什么会变慢（每段同步后的分段计时）**：一步拆成 快照 / 草稿 / 验证 / **失配重算** / MTP 回填 五段，16K、4-token 配置：

| 分段 | ms/步 | 占比 |
|---|---:|---:|
| 验证前向（4 个位置） | 223.9 | 51% |
| **失配重算** | **163.2** | **37%** |
| 草稿（3 次） | 31.2 | 7% |
| MTP 回填（约 3.25 次） | 22.0 | 5% |
| 快照 | 1.4 | 0% |
| 合计 | 442 | |

  第二位草稿只有 22–37% 命中，所以 78–88% 的步都要**回滚线性注意力状态、把已提交前缀重跑一遍**（Gated DeltaNet 的状态没法像 KV 那样截断）。2-token 第一位命中 87–100%、几乎从不重算（163 → 0），所以反而最快。**这是架构层面的代价，不是实现问题。**
- **25d. 更正：MTP 回填只要约 7 ms，不是 21 ms**。单次 `mtp(h, tok, pos, logits=False)` 实测 **6.99 ms**（整层含注意力 5.90、qkv 0.30、rotary 0.27、fc 0.14、两个 norm 0.34、其余 0.69）。之前读到的 21 ms 是**分段计时没有每段同步**、把验证前向的 GPU 尾巴算进了回填。**教训：分段计时必须在每个时间点前 `torch.cuda.synchronize()`，否则各段互相污染，结论全错。**

- **25e. 放宽验证判据（近似接受）**：16K、3 草稿、8 步 24 个草稿位、13 次失配。失配时 p(草稿)/p(主模型首选) 的中位数是 **0.000**，比值 ≥0.9 的 **0/13**、≥0.5 的 **1/13**、≥0.1 的 **2/13**。草稿错的时候离正确 token 很远（不是近似打平），放宽判据最多捞回 8% 的失配、省约 3% 时间，却会让输出不再是主模型的首选——**不划算，不采用**。根因：MTP 头是独立分布，错的时候是“另一个预测”，不像同模型早停层那样接近。

- **25f. LoopVQ（沿 loop 轴联合量化）在 16K 下的实测**：算子上可行——2-bit 码本反量化每层 0.437 ms（int8 是 0.324 ms），折算到一步 decode 只多 **+1.4 ms**（189 ms 的 0.7%）。但**质量在 16K 下不够**：循环段 KV 换成 2-bit LoopVQ 后 KL **0.314**、首选一致 92.6%，而 int8 KV 是 0.015 / 98.7%，连 4-bit 标量（0.174 / 94.2%）都更好。LoopVQ 的核心主张本身成立（同一比特率下"跨两遍联合编码"优于"单遍按通道"，1-bit 时 0.423 vs 0.612），但 16K 下 2-bit 的优势几乎消失（0.314 vs 0.322）。**结论：可行但不划算**——要追上 int8 得 4 bit 以上，那只能再省 0.24 GB，代价是 KL 差一个量级。

- **25g. LoopVQ 2-bit 加"最近 W 个 token 保持精确"**：16K、看序列末尾 96 个位置（更接近真实生成），三档窗口：W=0 **KL 2.187 / 首选 76.0%**；W=256 KL 2.373 / 74.0%；W=1024 KL 2.155 / 76.0%。**窗口没有帮助**（与 int8 的窗口实验一致）——误差摊在整段前缀上，保护末尾 1.5–6% 的位置无济于事。顺带一个更重要的发现：**2-bit 在序列末尾的 KL 是全序列平均的 7 倍**（2.19 vs 0.314），首选一致从 92.6% 掉到 76.0%——"全序列平均 KL"会显著高估 KV 压缩在真实生成里的可用性。评估 KV 精度必须看**末尾位置**。

- **25h. 延迟编码（新 token 先精确写，攒 N 个后再量化）**：16K、末尾 96 位置、参考精确 KV：N=0 **KL 0.0777 / 首选 96.9%**；N=8 0.0705 / 96.9%；N=32 0.0864 / 95.3%；N=128 0.0764 / 95.3%；（对照：最近 256 精确 0.0784 / 95.7%）。**全部在 ±11% 内、没有趋势**，差异是 96 个位置的采样噪声。成本侧也没有价值：单 token 的 KV 编码，标量 int8 只要 **0.83 ms**，256 码字最近邻 **0.60 ms**（比标量还快，因为标量要过 amax/除/取整三次），延迟编码最多省 0.6 ms/token ≈ 一步的 0.3%。**结论：延迟编码是为"编码很贵"的码本方案设计的，对我们是纯开销。**

- **25i. 逐格比特分配（LoopKV 的 P1）**：16K、末尾 96 位置。先逐格剖析敏感度：**只压第 1 遍（6 格）2-bit → KL 1.80 / 首选 81%；只压第 2 遍（6 格）2-bit → 0.33–0.39 / 88.5–90.6%**——第 1 遍比第 2 遍敏感约 **5 倍**，和 LoopKV 在 Ouro 上"第 1 遍比第 3 遍敏感 3 倍"同向且更强。于是分配定为**第 1 遍 int8 + 第 2 遍 int4**（其余 int8）：**KV 0.48 → 0.38 GB（−21%）**，末尾首选一致 **95.83% 与全 int8 完全相同**，KL 0.042 → 0.067（另一次噪声较大的跑是 0.123 → 0.307）。若第 2 遍降到 2-bit 则省 32%，但首选一致掉到 88.5%——不可接受。
  - **测量教训**：同一配置的末尾 KL 在三次跑里出现 0.044 / 0.173 / 0.044 的跳动（模型本身有非确定性），所以**末尾 KL 只能看量级和排序，不能当阈值**；首选一致率稳定得多，更适合做判据。

- **25j. 逐格分配的端到端实现（第 2 遍槽位 4-bit）**：`FixedKVLayer` 加了按槽位的 4/8 bit 选择，int4 用"每字节两个 4-bit 码 + 每 token 每头一个 fp32 缩放"打包。16K 实测：

| 配置 | KV | prefill | 投机 | 每步 | 整卡峰值 |
|---|---:|---:|---:|---:|---:|
| 全部 int8 | 456.8 MB | 50.2 s | 4.24 tok/s | 471 ms | 7.53 GB |
| **第 2 遍 int4** | **360.4 MB（−21.1%）** | 52.0 s | 3.99 tok/s（−5.9%） | 502 ms | **7.89 GB（+0.36）** |

  **存储目标达成**（0.48 → 0.38 GB，和预测一致）。融合解包内核（`int4_dequant.py`：读 uint8 直接写 bf16，逐位一致，每层 0.32 ms vs torch 的 5.6 ms）去掉了临时张量，**本进程峰值净降 0.10 GB**。但加了预热之后重测（64 token、32/24 步），**速度代价是真实的 −18%**：

| 配置 | KV | 投机 | 命中 | 每步 | 本进程峰值 |
|---|---:|---:|---:|---:|---:|
| 全部 int8 | 456.8 MB | **10.78 tok/s** | 30/32 | **185 ms** | 5.72 GB |
| 第 2 遍 int4 | **360.4 MB（−21%）** | 8.80 tok/s | 22/24 | 303 ms | **5.62 GB** |

  **最终干净 A/B（16K、全 NF4 + NF4 MTP、预热 5 次、64 token、一进程一缓存）**：

| 配置 | KV | 投机 | 命中 | 每步 | 本进程峰值 |
|---|---:|---:|---:|---:|---:|
| 全部 int8 | 456.8 MB | 9.85 tok/s | 31/32 | **203 ms** | 5.72 GB |
| **第 2 遍 int4** | **360.4 MB（−21%）** | **9.84 tok/s** | 30/32 | **203 ms** | **5.62 GB** |

  **同速、少 96 MB。** 复跑一次 int4 得到 328 ms/步（8.13 tok/s）——同配置的抖动来自上面说的显存放置，不是格式差异。

  **结论：省 96 MB，速度在噪声内。** 解包内核的代价（~4 ms/步）被测量噪声淹没。之前"int4 慢 18%"的结论作废。
  - **为什么 16K 的数字会抽签**：干净对照（一进程、位置递增、每次同步）显示 **8K 下 int8 与 int4 只差 ±3%**（95.1 vs 97.0 ms），而 16K 下同一进程里 **int8 的第二次测量也会从 98.7 掉到 671.6 ms**——所以不是格式问题，是整卡到 7.7/8.59 GB 后驱动把新分配的大块放到较慢内存，之后每步内存受限（利用率 97% 但功耗只有 46–78 W）。`expandable_segments` 无效，不是 PyTorch 碎片。
  - **16K 测速的硬性前提**：整卡余量 ≥1.5 GB（关掉浏览器/微信/Steam），一个进程只建一次大缓存；做 A/B 优先用 8K。
  - **⚠️ 测量教训（又一次）**：同一配置不加预热是 **4.23 tok/s / 473 ms/步**，加 5 次 1/2-token 预热后是 **11.79 tok/s / 170 ms/步**——**差 2.8 倍**。预热期 GPU 频率已钉在 2460 MHz、利用率 97%、功耗 46–78 W、本进程峰值只有 5.72 GB，所以既不是降频也不是爆显存，就是**冷启动**（内核 autotune + 16K KV 缓冲首次缺页）。任何投机解码的测速都必须先预热，否则数字全废。
  - 当日机器状态：同一份"全 int8 + 2-token 投机"的配置此前测到过 10.8 tok/s，本次只有 4.2 tok/s（峰值 7.53 vs 6.7 GB），**绝对速度不可比，只看相对差异**。

- **25k. 混合 int8 权重在 16K 下终于放得下了（但只剩 80 MB）**：全 NF4 + NF4 MTP + 第 2 遍 int4 KV 的组合下，换成 `mixed_plan_1.0`（+1.0 GB，KL 0.146 → 0.078）：

| **int8 混合，16K** | 360 MB | **6.58 GB** | **8.51 GB（99%）** | 7.94 tok/s | 252 ms |
| int8 混合，8K | 181 MB | 6.44 GB | 8.50 GB | 9.15 tok/s | 292 ms |

  **结论：技术上放得下，但整卡 8.51/8.59 GB 只剩约 80 MB 余量**——再开一个浏览器标签就可能崩，`VramGuard`（97% 阈值 = 8.33 GB）也会把它判为越界。**加了 `empty_cache()` 后复测**（其他程序只占 0.96 GB）：投机 **8.50 tok/s / 235 ms 每步**（29/32 命中），本进程峰值 6.58 GB，但**整卡仍然是 8.59 GB（100%）**——我们自己的净占用约 7.6 GB，加上别的程序就顶死了。**建议：要更高精度就用 8K 上下文 + int8 混合权重；要坚持 16K 就保持全 NF4。**

- **25l. 模型自己占多少显存（扣除其他程序）**：16K、全 NF4、第 2 遍 int4 KV，分阶段实测（`probe_footprint.py`）：

| 阶段 | 本进程分配 | 保留 | 整卡 | 净占用（减启动 1.17 GB） |
|---|---:|---:|---:|---:|
| 启动 | — | — | 1.17 | 0 |
| 加载全 NF4 权重 | 4.50 | 4.51 | 5.70 | 4.53 |
| MTP 头（bf16） | 5.05 | 5.58 | 7.25 | 6.08 |
| MTP 量化成 NF4 | 4.70 | 5.58 | 7.23 | 6.06 |
| **`empty_cache()` 之后** | 4.70 | **4.95** | **6.14** | **4.97** |
| KV 就位 | 5.15 | 5.23 | 6.43 | 5.25 |
| prefill 峰值 | 5.25 | 5.81 | 7.50 | **6.32** |

  所以 **模型净占 6.3 GB**（16K）：权重 4.50 + MTP 0.14 + KV 0.36 + scratch 0.064 + MTP KV 0.067 + 激活约 0.5 + 分配器保留约 0.6。换 int8 混合权重（+0.97）→ **净 7.3 GB**，整卡就会顶到 8.59。
  - **一个白捡 1.1 GB 的操作**：量化完 MTP 头之后调 `torch.cuda.empty_cache()`，PyTorch 的"保留未用"从 5.58 → 4.95 GB，**整卡从 7.23 掉到 6.14**。不调的话这部分会被一直占着（我们之前的端到端测试都没调，白背了约 1 GB）。

## 26. 三条部署路径（按显存预算选）

所有路径都基于：全 NF4 或混合 int8 权重 + NF4 MTP 头 + 闭式解 Sinkhorn + 融合解包 + 2-token 自投机，KV 均为"第 2 遍 int4、其余 int8"。

| 路径 | 权重 | 上下文 | KV | 本进程峰值 | 整卡峰值 | 速度 | KL |
|---|---|---|---:|---:|---:|---:|---:|
| **A. 稳 16K** | 全 NF4（4.50 GB） | 16K | 360 MB | 5.62 GB | **7.5–7.7 GB** | **9.8–12.0 tok/s** | 0.146 |
| **B. 稳 8K** | int8 混合（5.47 GB） | 8K | 181 MB | 6.44 GB | ~7.4 GB | 9.15 tok/s | **0.078** |
| **C. 赌 16K** | int8 混合（5.47 GB） | 16K | 360 MB | 6.58 GB | **8.59 GB（100%）** | 8.50 tok/s | **0.078** |

**怎么选**

- **A 是默认**：整卡留 0.9–1.1 GB 余量，速度最高（9.8–12.0），代价是权重精度最低（KL 0.146）。
- **B 要质量**：同样的速度量级（9.15）换到 KL 0.078，但上下文只有 8K。
- **C 两个都要**：能跑，但整卡 100%，余量为零——多开一个网页就可能崩，`VramGuard` 也会判越界。**不建议作为常驻配置**。

**为什么会出现"二选一"**：16K 下模型自己净占 6.3 GB（全 NF4）/ 7.3 GB（int8 混合），加上其他程序 1–2 GB，8.59 GB 的卡只够放下前者。省下的每一块都算数：MTP 头 NF4（−0.35）、KV 第 2 遍 int4（−0.10）、`empty_cache()`（−1.1 的分配器浪费）——正是它们把 A 从"跑不起来"推到"有 1 GB 余量"。

**中间方案（未做）**：从 `mixed_plan_1.0` 里取敏感度最高的一半，做一个 +0.5 GB 计划（KL 约 0.11），16K 下净占用约 6.8 GB、整卡 7.8–8.0 GB，可留 0.5 GB 余量。

- **25m. 换 WSL2（Linux）跑并没有更快**：同一模型、同一脚本、同一时刻对比（16K、全 NF4、第 2 遍 int4 KV）：Windows **1-token 170.6 ms / 2-token 170.5 ms / 投机 10.23 tok/s（196 ms/步）**；WSL2 Ubuntu **173.6 / 177.0 / 9.62 tok/s（208 ms/步）**，命中都是 12/12，GPU 都在 2460 MHz、90%+ 利用率。**WSL 反而慢 2–6%**。说明 16K 的一步是 GPU 工作主导，操作系统调度占比很小；"换 Linux 白拿 10%"的假设不成立——那 10% 要靠**变长 CUDA graph + 融合内核**去拿，而不是换系统。（WSL 环境的搭建过程与网络坑见 `docs/WSL.md`。）

- **25n. 把 int8 KV 接进 Graph2Decoder：8K 下稳态 +14%，16K 放不下**：`Graph2Decoder(kv_int8=True, qlen=2)` 本来就支持 int8，写了一个等价的 2-token 投机循环（每步固定提交 2 个 token，失配时提交模型自己的纠正 token）端到端对比：

| 上下文 | 路径 | 稳态每步 | 稳态速度 | 捕获 | 整卡 |
|---|---|---:|---:|---:|---:|
| 8K | eager（生产） | 176 ms | 11.39 tok/s | — | 7.34 GB |
| 8K | **graph（int8 KV）** | **155 ms** | **12.94 tok/s（+14%）** | 3.9 s 一次性 | 7.34 GB |
| 16K | graph | ~185 ms | ~10.8 tok/s | 4.2 s | **8.02 GB** |
| 16K | eager | — | — | — | 8.59 GB（分页，测不准） |

  - **生成 token 与 eager 逐字一致**（32/32、24/24），说明投机逻辑接对了；
  - 8K 下图的收益真实存在：**+14% 稳态**，但捕获 3.9 s，按每步省 21 ms 算，**约 370 个 token 才回本**；
  - **16K 下图的额外开销（图私有池 + 对齐缓冲约 0.4–0.5 GB）把我们推进分页区**，所以 16K 目前用不了——要先把显存腾出来（8K 上下文、或去掉 MTP、或更小的 max_len）。

  - **16K + 第 2 遍 int4（最优 KV 配置）**：图路径稳态 **207 ms/步 = 9.68 tok/s**、峰值 **7.90 GB**、捕获 4.1 s；同配置生产 eager 是 **203 ms/步 = 9.84 tok/s**、峰值 7.73 GB。**两者打平（差 2%），图没有收益**——因为固定 pad 的掩码开销随上下文线性增长，把固定约为 10 ms 的启动节省吃掉了。但 int4 在这里有额外价值：它把图路径从 8.02 GB 拉回 7.90 GB，**刚好躲开分页区**（不压 int4 时图路径会掉到 4.5 tok/s）。
  - 汇总：**图只在 ≤8K 划算（+14%），16K 打平，捕获 4 s 需 ~370 token 回本。**

- **25o. 16K 的内核级剖析：GPU 只占 ~50 ms，一步 170 ms 是 CPU 提交瓶颈**（`prof_16k_tail.py`，5 步平均）：

| 算子 | ms/步 | 次数/步 |
|---|---:|---:|
| `aten::copy_` | 11.1 | 286 |
| `bitsandbytes::gemm_4bit` | 8.8 | 87 |
| `_efficient_attention_forward` | 5.8 | 2.8 |
| `aten::mul` | 3.1 | 198 |
| `aten::cat` | 1.9 | 78 |
| `aten::add` / `to_copy` / `to` / `mean` / `rsqrt` / `stack` … | ~10 | 数百 |
| **GPU 合计** | **~50** | |

  而同一状态下 1-token 前向的**墙钟是 170 ms**——也就是说**约 120 ms 花在 CPU 侧提交与 Python glue 上**，不是 GPU 算不动。这解释了为什么"融合内核"单做没感觉（GPU 只占 30%），也解释了为什么我们的图在 16K 没收益：图的准备（16K 掩码填充、14 次 idx 拷贝、MTP 三次调用、快照保存/恢复、lm_head）仍然留在图上、由 Python 每步执行。
  - **正确的做法**：把这些准备也搬进图里（掩码用设备端下标在核内算、idx 更新由核内完成、MTP 也捕获），或者干脆消掉（自写无掩码注意力）。
  - 只有 50 ms 的 GPU 时间意味着**理论上限是 ~20 tok/s**（50 ms/token），前提是把 120 ms 的提交成本压掉。

- **25p. 把准备搬进图：先拿到 +4.5%，但还有 ~90 ms 没解释**：16K、图路径、分段计时（ms/步）：

| 分段 | 优化前 | 优化后 |
|---|---:|---:|
| `dec.step`（准备 + 重放 + lm_head） | 500（含捕获摊薄）→ 稳态 ~175 | ~175 |
| MTP 草稿 | 8.5 | 6.1 |
| MTP 回填（两次单 token → 一次 T=2） | **25.2** | **16.8** |
| 快照 | 0.4 | 0.4 |
| **稳态合计** | **211 ms（9.48 tok/s）** | **202 ms（9.91 tok/s，+4.5%）** |

  - 已知 `g.replay()` 单独只要 **85.6 ms**（2 token），所以 `dec.step` 里还有 **~90 ms 不在重放上**；而掩码填充（16 KB 布尔）和 14 次 idx 拷贝理论上都 <1 ms，这块需要往 `step` 内部再插一层计时才能定位。
  - token 与 eager 仍然逐字一致（24/24）。

- **25q. 更正 25o：那 90 ms 就是图重放本身，准备部分可以忽略**（`probe_step_parts.py`，16K、2 token）：

| 分段 | ms/步 |
|---|---:|
| embedding（SSD 读 2 行） | 0.13 |
| 写入 embedding 缓冲 | 0.03 |
| **掩码填充（16K 布尔）** | **0.05** |
| idx 填充（14 层） | 0.19 |
| **图重放** | **162.3** |
| lm_head（2 行 × 248k） | 4.95 |
| **合计** | **167.8** |

  也就是说：**"把准备搬进图"没有意义**——掩码 0.05 ms、idx 0.19 ms、embedding 0.16 ms，加起来 0.4 ms。之前以为的 90 ms 缺口，实际是**图重放量成了 162 ms 而不是早先一次测到的 85.6 ms**（那次是在更宽松的显存状态下测的）。
  - **更正 25o**：那次 profiler 报"GPU 只有 50 ms"是被 profiler 自身的调度影响低估计了。真实的一步 ≈ 167 ms **就是 GPU 工作**（56 次层执行 + 16K 掩码注意力），不是 CPU 提交。
  - 结论：16K 下图与 eager 打平（167 vs 170），因为**两者的 GPU 工作量相同**，图的收益（省启动）本来就只值几个百分点。

- **25r. 元素级融合（RMSNorm + SiLU×up）：单步 −5%，但端到端还没对上**：两个内核都**逐位一致**（RMSNorm 早先验证 141/141 调用；新写的 SiLU×up 在 5.6M 元素上 0 差异，用了 PTX `cvt.rn.bf16.f32` 做舍入栅栏）。16K、1-token 前向、顺序反转过的 A/B：

| 配置 | ms | 相对基线 |
|---|---:|---:|
| 基线 | 165.6 / 166.4 | — |
| + 融合 RMSNorm | 157.7 | **−4.8%** |
| + 融合 RMSNorm + SiLU×up | 157.4 | **−4.9%** |
| 只开 SiLU（关 RMSNorm） | 161.7 | −2.4% |
| （反转顺序）融合先 / 基线后 | 157.4 / 166.4 | **−5.4%** |

  但**端到端看起来"token 不一致"**：同一条命令，`SENSENOVA_FUSE=0` 是 10.00 tok/s（200 ms/步，31/32），`=1` 是 8.31 tok/s（321 ms/步，22/24）。做了最小对照（同一 16K 上下文、teacher-forced 同一批 token，逐步比 logits）：

| 模式 | 第 1 步 logits 最大差 | 首选一致 |
|---|---:|---:|
| **基线（重跑）** | **1.26e+01** | **1/5** |
| 只 RMSNorm | 1.09e+01 | 1/5 |
| 只 SiLU | 1.22e+01 | 1/5 |
| 两个都开 | 1.28e+01 | 1/5 |

  **基线自己重跑就不一致，量级和融合版完全一样**——所以那些差异来自**模型在 T=1 decode 下本身不确定**（bnb 4-bit GEMV 的 split-k、FLA 的原子加），不是融合造成的。两个内核各自是逐位一致的（RMSNorm 141/141 调用、SiLU×up 5.6M 元素 0 差异）。
  - 因此**融合恢复默认开启**；但记住：**T=1 decode 的端到端 A/B 必须重复多次**，单次命中数（31/32 vs 22/24）不能当判据。

- **25s. 162 ms 的重放合不合理：能对账，但不均衡**（`bench_layer_cost.py`，16K、1 token、单层计时）：

| 层类型 | 单次 | 次数 | 合计 |
|---|---:|---:|---:|
| **全注意力层**（L3 为代表） | **7.35 ms** | 14 | **103.0 ms** |
| 线性注意力层（L0 为代表） | 1.46 ms | 42 | 61.4 ms |
| **合计** | | | **164.4 ms**（实测重放 162–170 ms ✓） |

  所以 162 ms **不是异常**，就是 56 次层执行的累加；但**结构很不均衡**：14 次全注意力执行只占 25% 的次数，却吃掉 **63%** 的时间，每次 7.35 ms，是同层线性注意力的 **5 倍**。
  - 7.35 ms 粗拆：注意力 2.2 ms（掩码不影响，2.21 vs 2.24）、KV 反量化 0.64、GEMV ~1.1、元素级 ~0.6，**还有约 2.8 ms 没解释**——下一步该单测这一个层的内部。
  - 这也解释了"融合内核"为什么只值 5%：元素级只占 ~0.6 ms/层。

## 试过但没有提升（一句话）

- **1. 直接 4-bit 加载到 GPU**：让模型第一次跑起来，但显存 9.04GB 超限、只有 1.6–1.8 tok/s，只是起点。
- **3. 安装 flash-linear-attention**：输出逐字相同、速度几乎没变（1.8–1.9 tok/s），但没有它后面所有线性注意力路径都跑不动，属于必要的地基。
- **6. 数学题为什么答错**：结论是错误来自模型不写中间步骤时的心算能力，与量化无关（开思考后 8/8）。
- **8. NF4 与 bf16 逐位置对比**：建立了评测方法（KL 均值 0.12、首选一致 87%、困惑度 +3.1%），本身不提升速度。
- **15. 合并两遍循环的激活做 int8 校准**：代理指标好 17%，但端到端 KL 0.0785 → 0.0779（在噪声内），不值得改流程——int8 的误差只有 1.1e-4，KL 几乎全部来自剩下的 NF4 层。
- **16. 砍掉第 2 遍循环**：KL 0.078 → 2.28、首选 88% → 47%，方向关闭（状态相对距离 0.83，远未收敛）。
- **18. LoopKV 的 KV 压缩**：decode 不受 KV 带宽限制（注意力+softmax 只占 0.54ms/步），它的"逐单元伤害相加"前提在本模型的权重精度上也不成立（高估 30%）。
- **19. 一次验证 4 个 token**：链式草稿第 2/3 位命中掉到 50%/21%，单独实测 ×0.93，比普通解码还慢；要第 2、3 位都 ≥0.8 才划算，而 MTP 只训练过一步预测。
- **20. k 行 NF4 GEMV**：bnb 原生多行已经是一次读权重，自写内核更慢（344µs vs 154µs）；副产品是发现 `small_batch_gemv` 有害（见第 21 步）。
- **21b. 线性注意力短序列特化**：把 T≤4 的分块算法换成递推内核，只快 1.02×，且数值不等价（KL 9.2e-2、首选一致 50%），不启用。

## 测量纪律（踩过的坑换来的规则）

1. **一次只测一个配置，一个进程只留一个 KV 缓存。** 两条路径放在同一个进程里会同时占两份 KV/缓冲区，整卡被推到 8GB 以上、Windows 开始把显存换到内存，结果能差 **2.6 倍**：同一份 eager 代码，双缓存下 3.75 tok/s，单缓存下 **9.68 tok/s**。历史脚本 `test_short_linattn.py`、`test_gemv_patch_ab.py`、`cmp_spec.py` 是这种"同进程对比多配置"的写法，只作参考，**新测试一律一个配置一个进程**（`test_graph_spec.py` 已按这个方式改）。
2. **参照数据不要放显存**：搜索集/验证集的 bf16 参照（约 2.5GB）放在 GPU 上会把显存挤满，每组从 10 秒变成 100–300 秒。改为放内存、用到时再送 GPU。
3. **切换精度前后要 `gc.collect()` + 清缓存**：NF4 和 int8 来回切换时，bnb 的 4-bit 参数和所属层互相引用，旧层要等 GC 才释放，切换 40 多次就把显存挤满。
4. **结果异常时先看 `nvidia-smi`**：利用率 100% 但功耗只有约 30W，说明它在等数据搬运而不是在计算；整卡接近 8GB 时任何速度数字都不可信。

## 未完成 / 已知问题

1. **按整卡显存重选混合精度方案**：+2.0GB 超限，+1.0GB 还需要测一次短 prompt 下的整卡占用。
2. **元素级长尾融合**：一步 110ms 里约 60ms 是几千个元素级小算子，是现在唯一还没试过的大杠杆（对单层做 `torch.compile`，或手写融合 mHC 的 `mul/add/cat`）。CUDA Graph 解决提交、融合解决执行。
3. **MTP 头量化成 NF4**（约省 0.35GB），让 32k 上下文和自投机解码能同时开。
4. **CUDA Graph 的覆盖**：8K/32K 未测（两条路径的缓存同时存在会超 8GB）；4-token 验证的图未实现。
5. **memhog 锁定 8GB 内存实测**；**非循环模型对照**（Qwen3.5-9B）确认循环结构是否让量化损失更大。
6. Sinkhorn 和 Triton 内核首次编译约 15 秒，可以做编译缓存。
